Intent: claims status self-service

Author: J. Ortiz, claims operations
Problem

Customers phone the contact center to ask where their claim is. Handlers spend roughly a third of call time on status-only queries.

Proposed outcome

Customers see claim status, next step and expected date in the portal.

Affected users and systems

Claims handlers, the portal team, the claims-core API.

Constraints

No new PII in the portal session. Existing authentication only.

Open questions

Do third-party loss adjusters need access too?

Prerequisites

None. You can start with the next item.

Infrastructure

  • Claude access for non-engineers (claude.ai or Cowork)
  • An agreed intent.md template
  • A shared, version-controlled home for intent that the product owner watches

The intent home

The simplest home is an intent/ folder in the product repo. A dedicated intent repo only pays off when intent spans many repos. In a monorepo it is a directory.

A technical person stands it up once and decides who can write to it. Contributors without Git experience can skip Git: a connector such as GitHub lets Claude commit the Markdown for them.

  1. Originator describes the problem in their own words.
  2. Claude brainstorms with them until it is concrete, asking about scope, users, constraints and success.
  3. Claude writes intent.md using the org template.
  4. Originator corrects any misunderstanding.
  5. Commit to the shared home. Author and timestamp join the record. The product owner picks it up.

Key takeaways

  • intent.md is a proto-spec in the originator's own terms. It can start from an idea, a ticket or an alert.
  • Claude asks the analyst's questions, so the originator does not hand the idea to a chain of owners.
  • The product owner reviews and corrects it before it is committed. Humans make the accept or close call.
  • The setup is small: Claude access, a template, and a shared intent home.
  • Measure time to a committed intent.md, and the share the product owner accepts.
