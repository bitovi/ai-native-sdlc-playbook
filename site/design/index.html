Traditional

Separate phases, separate teams

Analysts formalize requirements and designers parse them back into a design. The separation exists for accountability, but it is slow and lossy.

AI-native

One prompted session

Claude takes intent.md and produces a spec constrained by the org's skills, with areas of concern flagged.

Prerequisites

An accepted intent.md, and brand, security, compliance and UX policies written as skills.

Infrastructure

A product owner with Claude access. No engineering skill is required.

  1. Product owner opens a session with the org's skills available and attaches intent.md.
  2. Claude gets a prompt that points at the intent, names the constraints and demands flagged concerns. See the three ways to start it below.
  3. Product owner reviews the spec against the idea.
  4. Product owner works through the flagged concerns first, with each policy owner.
  5. Commit spec.md alongside intent.md.
  6. Product owner decides if spec and intent proceed to build. A tech lead is consulted for higher-risk items.

A front-end variant

After intent.md is accepted, the product owner mocks up the design in Claude Design from the intent, iterates, then exports to Claude Code to build. The course marks Claude Design as beta.

How it gets triggered

Start by hand, then automate

Adoption has three rungs. Each one removes a manual step.

1

A manual prompt

The product owner runs the prompt by hand in a session with skills and intent.md attached.

2

An org slash command

The prompt is codified as an organization-level slash command, so everyone runs the same pass.

3

Triggered on merge of intent.md

Accepting intent.md fires a non-interactive job. The product owner's first involvement is the review.

Merge intent.md→ Job runs the pass with skills loaded→ spec.md opened as a pull request

The CI/CD play in Stage 5 covers the plumbing.

Key takeaways

  • Requirements and design happen in one session, with Claude drafting and the product owner reviewing.
  • Brand, security, compliance and UX policies are skills, so they constrain the spec as it is written.
  • Flagged concerns go to named policy owners before engineering sees the spec.
  • Start with a manual prompt, then an org slash command, then a job that runs when intent.md merges.
  • Measure the time from intent.md to spec.md, and how often the spec changes after planning begins.
