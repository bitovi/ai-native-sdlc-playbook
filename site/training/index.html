Lesson 1 of 6

The shift

5 minRead 2 minActivity 3 minDone

AI now writes code fast. The process around the code has not kept pace: approval gates, reviews, and handoffs still run at human speed. So the bottleneck moves to plan, review, test, and deploy.

  • Most teams run six stages: plan, design, build, test, deploy, and maintain.
  • In the AI-native SDLC the straight line becomes a loop, with AI at each stage and handovers automated.
  • Each stage ends by committing a file, and the next stage starts by reading it: intent.md spec.md plan.md, then the diff and tests, the PR, and the incident record.
  • The chain of commits is the audit trail: who asked, what the agent made, and who approved.
  • People stay accountable for every decision that needs judgment.
Triggers between stages
  • An accepted intent.md starts design.
  • An approved spec.md starts plan mode.
  • A merged PR starts the pipeline.
  • A breached control band writes the next intent.md.

Lesson 2 of 6

Plan: capture as intent.md

5 minRead 2 minActivity 3 minDone

intent.md is a short, version-controlled file that says what is wanted, why, and under which constraints. People can read it, and the next stage can act on it.

  • It starts from an idea, a ticket, or an alert.
  • Originator describes the problem in their own words. No formal language needed.
  • Claude asks the analyst's questions: scope, users, constraints, and what success looks like. Then it writes the file from the team's template.
  • Product owner reviews and corrects it before it is committed. Accepting it starts design.
The template's five sections
  1. Problem
  2. Proposed outcome
  3. Affected users and systems
  4. Constraints
  5. Open questions

Lesson 3 of 6

Design and build

5 minRead 2 minActivity 3 minDone

  • Spec. Claude turns the approved intent.md into spec.md, guided by the team's skills for brand, security, compliance, and UX. It flags areas of concern. The product owner reviews the spec and does not write it.
  • Plan mode first. In plan mode Claude can read the code and cannot change it. The plan names the files, the order of work, and the tests. The engineer corrects it and commits plan.md.
  • CLAUDE.md. What a new joiner needs on day one: commands, the conventions that matter, and what Claude keeps getting wrong. Claude reads all of it at the start of every session. Keep it under a page. When Claude makes a mistake twice, the fix goes in.
  • Skill or hook? A skill holds a policy to apply consistently, and it is advisory. A hook is deterministic, for rules that must always hold.
Parallel sessions
  • Each session works in its own Git worktree.
  • Start with 2 or 3 sessions.
  • Add more only while review keeps up.

Lesson 4 of 6

Test: a feedback loop and evals

5 minRead 2 minActivity 3 minDone

Always give Claude a way to check its own work: tests, a build, or a screenshot diff. The session checks and fixes its work before an engineer sees it.

  • Wrap each check in one command, such as make test, and list it in CLAUDE.md.
  • Set a target you can measure, such as "all tests in test_status.py pass".
  • For a bug, write the failing test first. Then Claude makes it pass without editing the test.
  • Protect the loop: a hook blocks edits to test files during a fix.
Continuous evals in CI
  • Collect 20 to 50 real tasks with their accepted outcomes.
  • Run them in CI on a schedule and on any change to CLAUDE.md, skills, or hooks.
  • Each production incident gets an eval that stays as a regression test.

Lesson 5 of 6

Deploy: review, gates, and pipelines

5 minRead 2 minActivity 3 minDone

  • AI in PR review. Claude reviews every PR in the passes set in REVIEW.md: bugs, security, and compliance with spec.md and plan.md. It ranks findings as Important or Nit, with at most five nits per review.
  • Findings do not approve or block a PR on their own. A code owner approves through branch protection. The agent that wrote the code has no way to approve it.
  • Hooks as approval gates. A hook is a script that runs before Claude acts and can allow, ask, or block. A block names the route to approval.
  • CI/CD. Claude runs in the pipeline for judgment steps, in a sandbox. Everything it writes arrives as a PR. Deploy, status, and rollback are tools per environment.
Autonomy by environment
  • Dev: the agent deploys freely.
  • Staging: the hook asks, or allows from the pipeline on main.
  • Production: the agent prepares the release and the release manager authorizes it.
  • Rollback is the most rehearsed path.

Lesson 6 of 6

Maintain: close the loop

5 minRead 2 minActivity 3 minDone

A deterministic script watches one metric. No model is involved in detection. The baseline is the mean of the last 30 days of hourly readings, and sigma (σ) is the standard deviation.

  • 1σ: only log. Readings land here often by chance.
  • 2σ: Claude diagnoses, read-only.
  • 3σ: Claude may act, only by opening a PR into the review gate or by running a pre-approved runbook such as rollback.
  • Slow drift counts as 2σ: four of the last five readings above 1σ, or eight in a row above the mean.
  • Claude writes its diagnosis as a new intent.md. The service owner triages it: fix now, schedule, or dismiss.

How it works

  • You see one question at a time. Use Previous and Next, or jump with the question map.
  • Flag a question to come back to it later.
  • The timer starts when you press Start. At zero, the exam submits itself.
  • Question formats: pick one, select all that apply, put in order, and match. A question counts as right only when every part is right.
  • You see no right or wrong answers until you submit. Then you get your score, a breakdown by stage, and the reason behind every answer.
  • Questions and options are shuffled on each attempt.
