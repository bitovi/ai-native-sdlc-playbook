Plan mode first

Engineers start in plan mode with the approved spec. The plan is committed as plan.md.

Traditional

The engineer reads the design and starts coding. Which files change and which tests to write stay in their head or a ticket comment, so nobody else can review it. The reviewer first sees the finished diff, and by then rework is slow.

→

AI-native

Work starts with a written plan from plan mode, where Claude can read the codebase but cannot change anything. The engineer corrects the plan. The approved version is committed as plan.md for later stages to check against.

Prerequisites

The intent artifact (intent.md or spec.md), if one exists.

CLAUDE.md helps.

Infrastructure

Claude Code with repo access.

  1. Start the session in plan mode.
  2. Give Claude intent.md and spec.md. Ask for a plan that names the files that change, the order of the work, and the tests that prove it.
  3. Interrogate the plan: what could this break, which step is the riskiest, which other options were rejected.
  4. Iterate until an engineer who never saw the conversation could implement from the plan alone.
  5. Commit the approved plan as plan.md. It joins the audit trail, and the PR review play checks the diff against it.
  6. Accept the plan and let Claude implement.
  7. If the implementation departs from the plan, update plan.md in the same commit. Consider a hook to enforce the sync.
Example plan.md (claims status)
  • Files that change: StatusPanel.tsx (new), claims-api/routes/status.py, claims-api/tests/test_status.py.
  • Order of work: the status endpoint behind existing auth, then the panel with a 60-second cache, then wire it into the portal nav.
  • Risks: claims-core allows 50 requests per second, so reads must be cached.
  • Proof: the tests cover the four claim states and fail on any extra field. A screenshot matches the approved mock.

The plan cites R1 to R4 and a spec concern, so a reviewer can check it line by line against the spec.

  • Design review happens before any code, when changing course is still a matter of editing a document.
  • Plan mode enforces this. Claude cannot edit files until the engineer accepts the plan.
  • The plan, its revisions and who accepted it are logged.
  • Routine changes are approved by the engineer. Higher risk goes to a tech lead or architect.
Leading
  • Share of changes that merge from the first implementation pass.
  • Time from plan approval to merged PR (from PR metadata).
Lagging
  • Rework cycles per change (PR metadata).
  • How often the merged diff still matches the committed plan.md.
Auto mode

Auto mode comes later, once guardrails mature

You iterate on and approve the plan. Claude then applies each change without a per-edit prompt. Auto mode becomes the default for routine work as these four guardrails mature:

A tuned CLAUDE.md
Skills that encode policy
Hooks that block unsafe actions
A test suite Claude can run
Auto mode for routine work
  • Good fit: a tight spec.md, a small blast radius, and code the tests already cover.
  • The shift is from watching the agent edit to reviewing artifacts after longer autonomous sessions.
  • With worktrees, auto mode enables parallelism across people and teams. The course calls it fundamental to running the SDLC autonomously and closing the loop in Stage 6.
Legacy systems

Fit around what exists: one source of truth per artifact

Teams already track work in Jira, requirements in a traceable tool, designs in Figma and approvals with a change board. Auditors accept these, so they are hard to replace. Start with linkage, then name one source of truth for each artifact.

spec.mdThe artifact in the repo notes the record ID
record ID →← commit SHA
Legacy recordJira, ServiceNow or a requirements tool holds the commit SHA

1. Linkage first

The minimum bar and a good place to start. Artifacts note the record ID. Legacy records carry the commit SHA of the Markdown file. There are two sources of truth, and that is accepted for now.

2. The repo is the truth

Markdown artifacts are authoritative. The legacy system references files within commits. One of the cleanest setups for engineering-led organizations: one tool, one timestamp authority.

3. The legacy system is the truth

Jira, ServiceNow or the requirements tool is authoritative. The Markdown files are working copies. Claude reads the record at session start and writes the outcome back through an MCP connector in the same session.

The choice can differ for each artifact. Both can coexist as long as they are linked or one is declared the source of truth.

Play 2

CLAUDE.md

2

CLAUDE.md

The context a new joiner needs, read by Claude at the start of every session.

What goes in

CLAUDE.mdStays under a page
Commands

make build, make test, make itest (needs docker), make lint (runs in CI), make run (portal on :3000, claims-api on :8000)

Conventions

claims-api is Python 3.12 and FastAPI. The portal is TypeScript and React. Every endpoint needs a test. Dates cross the API as ISO 8601.

Architecture

portal/, claims-api/ and intent/. Only claims-api talks to claims-core, which allows 50 requests per second. Cache reads, never poll it.

Things Claude gets wrong

Do not log request or response bodies in claims-api (they can hold PII). Do not bump dependency versions, the platform team owns them.

Claude reads all of it at the start of every session, so stale lines waste context. Example from the course's insurer claims portal.

Traditional

Knowledge lives in heads and wikis. A new joiner learns the conventions and the common mistakes by asking around.

→

AI-native

Claude reads a versioned file at the start of every session. The whole team maintains it and updates it each time Claude makes a mistake.

Prerequisites

None.

Infrastructure

A repo, Claude Code installed, and one engineer who knows the codebase well.

  1. Run /init in the repo. Claude generates a starting CLAUDE.md.
  2. Cut it down to what a new joiner needs on day one: build, test and lint commands, the conventions that matter, and the things Claude keeps getting wrong.
  3. Check it into Git at the repo root so the team shares one version and changes are reviewed like code.
  4. Working rule: when Claude makes a mistake twice, the correction goes into CLAUDE.md.
  5. Keep it under a page. Claude reads all of it at session start, and stale content wastes context.
  • It is version controlled, so the agent's instructions are reviewable and auditable.
  • Changes are logged in Git history.
  • Code owners approve changes in PR review.
  • The engineer owns the corrections.
Leading
  • How often Claude repeats a mistake that CLAUDE.md should have caught. Corrections are tracked in Git history.
Lagging
  • Time to first merged PR for a new team member (from PR history).

Skills as institutional knowledge

3

Skills as institutional knowledge

Rules that must apply the same way every time, owned by the people who own the policy.

Where does this rule go?

Place each rule in CLAUDE.md, a skill or a hook, using the course's guidance. Write a skill for institutional knowledge that must be applied consistently. Leave the rest in CLAUDE.md or a prompt.

CLAUDE.mdContext a new joiner needs: commands, conventions, architecture, common mistakes.
SkillInstitutional knowledge applied consistently. A control, though an advisory one.
HookThe deterministic layer. It blocks the action or puts the message in front of Claude.

Policy owners own the skill's source

Engineer

Traditional

Standards live in documents and in a few experienced heads. They are applied inconsistently, and violations show up late, in review.

→

AI-native

The instructions are explicit, version controlled, applied broadly, and updated centrally when policy changes. A skill carries the knowledge. A hook backs the rules that must always hold.

Prerequisites

None required. CLAUDE.md helps, but a skill does not depend on it.

Infrastructure

One policy with a named owner and a written source of truth.

  1. Pick one piece of knowledge that is enforced inconsistently today: a security standard, an API design convention or a brand rule.
  2. Write it as a skill: a folder with a SKILL.md whose frontmatter says when it triggers and whose body says what to do. An engineer writes it from the policy owner's source of truth, using Claude to help.
  3. Put it at .claude/skills/<name>/ so it ships with the code, or distribute it org-wide through a plugin.
  4. Test that it triggers by asking for the task in different ways.
  5. When policy changes, change the skill. The policy owner signs off.
  6. Engineers pick up the new version automatically in their next session.
Example secure-api-review skill

Use it when creating or changing external-facing endpoints. Four rules: authentication, input validation, audit events, and data classification (pii never in logs or errors). Then run scripts/check-endpoints.sh and include its output in the summary.

  • A skill is a control, though an advisory one. Nothing forces a session to comply.
  • A policy that must always hold needs something deterministic behind it: a hook that blocks the action, or a review pass at the PR.
  • The hook catches the violation at the edit. The same check on the PR catches anything that reached the branch another way.
  • Skill invocations are logged in session traces.
  • Policy owners own the source of truth for each skill and sign off changes. Skill changes are reviewed like code.
Leading
  • Time from the policy owner approving a change to the updated skill merging (a PR on the skill folder).
Lagging
  • PR review findings that cite the policy. They should fall toward zero. If they do not, the skill is not triggering or its text has drifted from policy.
Hooks

Hooks as build-time guardrails

A skill is advisory. The course says the skill makes violations rare and the hook makes them close to impossible. Most Claude actions in build are file edits and shell commands, so hooks fire most often here.

Block

Edits to protected paths, such as generated classes or a frozen package.

Tidy

Run the formatter and linter after edits.

Protect

Keep credentials out of the diff.

Back a skill

Back any skill whose policy must hold without exception.

  • A hook that asks a human for approval belongs in Stage 5. In build it puts a person back on the critical path of every parallel session.

Parallel sessions and subagents

Traditional

One engineer, one task at a time, with a lot of time spent on builds, tests and reviews. Switching tasks while waiting is tiring enough that few people choose to.

→

AI-native

One engineer runs several sessions at once, each in its own worktree. Repeated jobs become subagents. The job shifts to orchestrating, and eventually to building and monitoring loops.

Prerequisites

CLAUDE.md, because all sessions read it.

The Stage 4 feedback loop also helps. A session needs less supervision when it can verify its own work.

Infrastructure

A Git repo. Isolation comes from worktrees.

Permission settings tuned so sessions are not stuck on approval prompts for commands the org considers safe.

  1. Split work into tasks that touch different files, using the plan from plan mode to find independence. Tasks that share files run in one session, in order.
  2. Give each parallel task its own worktree, in separate terminals.
  3. Start with two or three sessions. Add sessions only while review is keeping up.
  4. Turn repeated jobs into subagents: Markdown files in .claude/agents/ with a name, a description of when to use it, and allowed tools. Check them into Git.
Example verifier subagent

Description: runs the app and checks the change works before the session reports done. Tools: Bash and Read. It starts the app, exercises the changed behavior and the two nearest neighboring flows, and reports what it ran and saw, including anything that differs from plan.md. It does not fix anything.

Other examples: a code simplifier and a researcher.

  • More sessions mean more output, so controls come from repo configuration.
  • Hooks and permission settings in the repo apply to all sessions.
  • Activity is logged and attributed to the engineer who ran it.
Leading
  • Concurrent sessions per engineer while review quality holds (counted from the OpenTelemetry export).
  • Share of the day spent steering rather than waiting.
Lagging
  • Changes merged per engineer per week, read alongside the rework rate (PR history).

Key takeaways

  • Start in plan mode. Claude reads, you correct the plan, then Claude implements. The approved plan.md joins the audit trail.
  • Keep CLAUDE.md short and shared. When Claude makes a mistake twice, the correction goes in.
  • A skill is advisory. Back any rule that must always hold with a hook and a check on the PR.
  • Start with two or three parallel sessions. Add more only while review keeps up.
  • With legacy systems, link first, then name one source of truth for each artifact.
